# План живого прогона на портале

> Last reviewed: 2026-07-29

Чек-лист для проверки приложения **на настоящем портале**. Нужен потому, что вебхук
(`pnpm b24:smoke`) работает вне контекста приложения и физически не может проверить главное:
регистрацию типа поля, хранилище настроек, рукопожатие плейсмента и события установки.

**Как пользоваться.** Идти сверху вниз, отмечать `[x]`. Где написано «ожидаем» — это то, что должно
получиться; если получилось другое, записать факт в колонку «что вышло» и не чинить на ходу.

**Что записывать по каждому пункту:** что сделали → что увидели → совпало ли с ожиданием. Скриншот
там, где помечено 📷 (эти же кадры пойдут в карточку Маркета). **Консоль фрейма держать открытой с
включённым Preserve log** и сохранять по каждому блоку: все недавние дефекты выглядели как «в
консоли есть, на экране нет».

| Что записать о прогоне | Значение |
|---|---|
| Дата, кто проводит | |
| Портал и его зона (`*.bitrix24.by` / `.ru` / …) | |
| Тариф портала | |
| Коммит сборки (`/api/health` → `commitSha`) | |
| `APP_EDGE_SECURITY` вкл/выкл | |
| `DATABASE_URL` задан? | |
| Браузер и версия | |
| Телефон и версия мобильного приложения | |

---

## 0. Перед началом

- [ ] Сборка выкачена и открывается по постоянному адресу (не туннель).
- [ ] `GET /api/health` отвечает 200. **Ожидаем** `ready.db`, `ready.oauth`, `ready.encryption` —
      все три `true`. Если нет — блоки 7 и 8 проверить нельзя, так и отметить.
- [ ] В логе старта строка `[boot] db=… oauth=… encryption=… keepalive=…` — записать её.
      **Ожидаем**, что в ней **нет** предупреждения про `B24_APPLICATION_TOKEN`. Заглушка в этой
      переменной выглядит здоровой и при этом отвергает каждую первую установку с 403.
- [ ] `DATABASE_URL`, `B24_CLIENT_ID/SECRET`, `B24_TOKEN_ENC_KEY` заданы (иначе часть блоков 5–7
      проверить нельзя — так и отметить).
- [ ] Тестовый портал **не тот**, на котором работают живые данные клиента.
- [ ] **Зона портала есть в `B24_ZONES`** (`server/utils/b24Rest.ts`). При `APP_EDGE_SECURITY=1`
      портал в неизвестной зоне даст пустой iframe вместо поля — и это будет выглядеть как поломка
      приложения. В консоли карточки ошибок CSP быть не должно.
- [ ] **Набор доступов у приложения, на котором идёт прогон, совпадает** с
      `MARKETPLACE_RELEASE.md`. На приложении с более широкими правами блок 4 ничего не доказывает.

## 1. Установка

- [ ] Приложение ставится с нуля, мастер доходит до конца без ошибок. 📷
- [ ] Тип поля зарегистрирован: **Настройки → Настройки CRM → Пользовательские поля**, в списке
      типов есть «Умная ссылка».
- [ ] Прерванная установка: закрыть мастер на середине, открыть `/install` ещё раз — **ожидаем**
      повтор без ошибок (шаг регистрации идемпотентный).
- [ ] Переустановка поверх существующей — **ожидаем** отсутствие дублей типа поля.

> ⚠ Самое ценное здесь — понять, доходит ли мастер до шага `event.bind`. Без подписки
> `ONAPPUNINSTALL` **не придёт вовсе**, и блок 7 провалится.

## 2. Настройка поля (цель — CRM)

- [ ] Создано поле-приёмник (тип «Число») и поле «Умная ссылка» на Сделке.
- [ ] В карточке видно новое поле; у администратора есть кнопка «Настроить поле». 📷
- [ ] В настройках **«Куда записывать связь» — это выпадающий список полей карточки**, а не поле
      ввода. **Ожидаем** там своё поле-приёмник.
- [ ] Сохранение работает, слайдер закрывается.
- [ ] Открыть настройки заново — **ожидаем** ранее сохранённые значения.
- [ ] Не-администратор кнопки «Настроить поле» не видит.

## 3. Работа поля в карточке

- [ ] Поиск: ввести часть названия → **ожидаем** список кандидатов. 📷
- [ ] Поиск по номеру записи.
- [ ] Привязка: нажать на название → **ожидаем** ссылку с названием и номером.
- [ ] Открытие: нажать на название связанной записи → **ожидаем** слайдер портала с этой записью.
- [ ] Создание: кнопка создания новой записи → **ожидаем** форму создания; после закрытия список
      обновляется сам.
- [ ] Отвязка → **ожидаем** возврат к подбору.
- [ ] **Высота поля**: карточка со связью не должна иметь под собой пустого места, а подбор не
      должен быть обрезан. 📷 *(проверяем `resizeWindowAuto`)*
- [ ] Режим редактирования карточки → **ожидаем** сообщение «Здесь поле не работает».
- [ ] Поле без настроек → **ожидаем** «Поле ещё не настроено» и кнопку у администратора.

## 3a. Когда портал не отвечает — главный блок

Все недавние исправления в коде были в путях ошибок, а happy path их не задевает: приложение может
пройти блок 3 целиком, имея все эти дефекты. Здесь мы ошибки создаём намеренно.

**Как ронять запросы:** DevTools → Network → правой кнопкой по запросу → Block request URL →
`*/rest/*`. Снимать блокировку там же.

- [ ] Карточка со связанной записью, запросы заблокированы. Нажать обновление в подборе →
      **ожидаем** сообщение **внутри поля**, рядом с действием. Название и номер связанной записи и
      кнопка отвязки **остаются на экране**. Полноэкранной страницы ошибки **нет**. 📷 Записать
      текст сообщения дословно.
- [ ] Снять блокировку, повторить действие успешно → **ожидаем**, что сообщение исчезло. Если оно
      висит над только что привязанной записью — дефект.
- [ ] Заблокировать запросы, нажать привязку у кандидата → **ожидаем** сообщение «карточка
      осталась без изменений». Снять блокировку, перезагрузить карточку → **связи действительно
      нет**. Записать, совпало ли сообщение с фактом.
- [ ] Заблокировать только `crm.item.list`, оставив `crm.item.update`, нажать привязку →
      **ожидаем** сообщение о неудачном **чтении**, а не о неудачной записи; после перезагрузки
      карточки связь **есть**.
- [ ] Заблокировать запросы и в другом окне сохранить настройки администратором → **ожидаем**, что
      карточка сотрудника не остаётся в бесконечной «крутилке». Записать, потребовалась ли
      перезагрузка.
- [ ] Запретить в браузере всплывающие окна для портала, нажать создание записи на цели-Списке →
      **ожидаем**: «крутилка» не зависла, подбор обновился, пользователю понятно, что произошло.

## 3b. Поле на неактивной вкладке карточки

- [ ] Перенести поле на вкладку карточки, которая **не открыта по умолчанию**. Открыть карточку,
      затем переключиться на эту вкладку → **ожидаем**, что поле отрисовалось. Полноэкранная
      страница ошибки на месте поля — дефект (ресайз при нулевой ширине).

## 3c. Высота — в цифрах, а не на глаз

DevTools → Elements → выбрать `iframe` плейсмента → `offsetHeight`. Записать три значения:

Высота теперь авто-замеряется по контенту (floor 85), поэтому ожидания — соотношения, а не
конкретные числа:

| Состояние | Высота | Ожидаем |
|---|---|---|
| Подбор кандидатов | | заметно больше 85 — таблица видна целиком, не обрезана |
| Связанная запись | | близко к 85 (без пустого поля под строкой) |
| Связанная запись + сообщение об ошибке | | больше, чем без сообщения |

Около 270 в состоянии «связанная запись» означает, что замеряется «крутилка», а не контент.

## 3d. Данные и границы

- [ ] После привязки закрыть и открыть карточку заново → связь на месте, **в самом поле-приёмнике**
      стоит номер связанной записи.
- [ ] Связать запись с названием в 200+ символов и запись с названием
      `<img src=x onerror=alert(1)>` → **ожидаем**: строка обрезается многоточием, высота не
      скачет, теги показаны как текст (никаких всплывающих окон). 📷
- [ ] Цель с более чем 50 записями: открыть подбор без поиска → записать, сколько строк показано и
      сказано ли, что список неполный. Найти по названию запись, заведомо не входящую в первые 50.
- [ ] Поиск **словом** (не числом) на цели-Списке → **ожидаем** кандидатов по названию.
      *(Проверено по REST: нечисловой фильтр по номеру ошибки не даёт, но на списке с данными
      поведение не проверялось.)*
- [ ] Строка, совпадающая и с номером записи, и с частью её названия → **ожидаем** одну строку, а
      не две.
- [ ] Два поля «Умная ссылка» в одной карточке с **разными** приёмниками → работают независимо,
      сохранение настроек одного не ломает второе. 📷
- [ ] Удалить поле-приёмник, оставив настройку → записать, что показывает поле. **Ожидаем**
      сообщение, из которого администратору понятно, что надо перенастроить.
- [ ] Открыть в обычной вкладке (вне портала) `<host>/handler/uf.smart-link`, `<host>/app`,
      `<host>/slider/app-options` → **ожидаем** внятную страницу, а не бесконечную «крутилку». 📷
- [ ] Два администратора (или две вкладки) сохраняют настройки **разных** полей: B сохраняет,
      затем A. Открыть настройки поля B → **ожидаем** настройки B. Если они откатились — **дефект,
      потеря данных**.
- [ ] **Переустановка поверх настроенного поля.** Связать запись, затем запустить установку ещё раз
      → **ожидаем**: поле на месте, тип не задвоился, настройки и связь целы, значение в
      поле-приёмнике не потерялось. 📷

## 6. Мобильный клиент и тёмная тема

- [ ] Открыть карточку в мобильном приложении Bitrix24: поле видно целиком, кнопки достижимы. 📷
- [ ] Подбор и привязка работают с телефона.
- [ ] Открытие связанной записи с телефона.
### Ответ по тёмной теме

Тема портала переключается в профиле пользователя (внешний вид). **Нужны четыре сочетания**, иначе
результат не интерпретируется: различие должно быть по теме **портала** при неизменной теме ОС.

В DevTools переключить контекст консоли на фрейм плейсмента (выпадающий список над консолью →
адрес нашего приложения) и выполнить:

```js
document.documentElement.style.colorScheme = 'light dark'  // иначе браузеру нечего наследовать
console.log(
  getComputedStyle(document.documentElement).colorScheme,
  matchMedia('(prefers-color-scheme: dark)').matches,
  getComputedStyle(document.body).backgroundColor
)
```

| Тема портала | Тема ОС | colorScheme | prefers-dark | фон body |
|---|---|---|---|---|
| светлая | светлая | | | |
| светлая | тёмная | | | |
| тёмная | светлая | | | |
| тёмная | тёмная | | | |

- [ ] Таблица заполнена. 📷 тёмного портала.
- [ ] Заодно вывести `$b24.placement.options` целиком и записать, есть ли там что-нибудь про тему.

**Вывод делаем только если значения различаются по строке «тема портала» при одной и той же теме
ОС.** Если различий нет — портал тему не пробрасывает, и автотема невозможна в принципе.

⚠ Честно про сам метод: это **проверка гипотезы, а не гарантированный ответ**. Мы читаем вычисленный
стиль своего же документа, а наши layout'ы тему пришпиливают сами. Если таблица выйдет однородной,
это может значить и «портал не пробрасывает», и «мы сами всё перекрыли». Поэтому в той же строке
выводим `$b24.placement.options` целиком: если тема приходит явным параметром, вопрос закрыт сразу и
без догадок.

## 7. Установка и удаление (OAuth, серверная часть)

Нужен `DATABASE_URL` и OAuth-креды. Без них блок пропускается — отметить это.

Как смотреть в базу — psql или консоль платформы; запрос:
`SELECT member_id, domain, left(refresh_token_enc, 20) FROM portal_tokens;`

- [ ] После установки в `portal_tokens` появилась строка для этого портала.
- [ ] В логе — исход вебхука установки, **без** идентификатора портала (только `portalHash`).
- [ ] `refresh_token_enc` в базе **не читается глазами** (зашифрован).
- [ ] Удалить приложение с портала → **ожидаем** приход `ONAPPUNINSTALL` и **исчезновение** строки
      из `portal_tokens`. *Это главный пункт всего блока.*
- [ ] После удаления в `portal_tombstone` появилась запись.
- [ ] ⚠ **Холодный старт.** Оставить сервер без запросов **больше часа** (платформа усыпляет
      процесс), затем удалить приложение → **ожидаем**, что событие всё равно доехало и строка
      исчезла. Битрикс события не ретраит, так что это единственная проверка против таймаута.
- [ ] Поставить приложение снова → **ожидаем** нормальную установку (тумбстоун не мешает).
- [ ] Без `B24_TOKEN_ENC_KEY` установка отвечает 503 и **не** сохраняет токен открытым текстом.

## 8. Попап оценки

⚠ Требует `DATABASE_URL`: без базы сервер всегда отвечает «не показывать», и это легко записать
как дефект.

- [ ] Задан `NUXT_PUBLIC_B24_MARKET_CODE`, открыть `/app` из меню приложений портала → попап
      появляется. 📷
- [ ] Кнопка открывает страницу приложения в Маркете портала.
- [ ] Открыть `/app` ещё раз → **ожидаем**, что попапа нет (порог повтора — несколько дней). Чтобы
      отличить «троттлится» от «сломано», посмотреть `prompted_at` в таблице `app_rating`.
- [ ] Код Маркета не задан → попапа нет вовсе.

## 8a. Обратная связь

Отдельный экран с **ослабленной** политикой безопасности и внешним скриптом Битрикса.

- [ ] Открыть «Написать нам» из шапки на `/app` → **ожидаем** форму, а не пустой блок. В консоли
      нет ошибок CSP. 📷
- [ ] Пройти по всем экранам приложения и убедиться, что нигде на подписи не видно технического

## 9. Публичные страницы

- [ ] `/` открывается вне портала, индексируется (есть заголовок и описание). 📷
- [ ] `/privacy` открывается по прямой ссылке, без портала и без JS.
- [ ] В подвале есть ссылки: Маркет, политика конфиденциальности, поддержка. Ссылка на Маркет
      ведёт в каталог **своей зоны** (`NUXT_PUBLIC_B24_MARKET_ZONE`) и открывает карточку
      приложения, а не пустой каталог.
- [ ] На `/privacy` есть раздел «Контакты» с адресом. Пустой заголовок без адреса — дефект
      конфигурации: значит, `NUXT_PUBLIC_SUPPORT_EMAIL` не задан на сборке.
- [ ] На `/privacy` в консоли **не грузится** чанк SDK Битрикс24 (Network → фильтр по размеру;
      ~300 КБ чанка быть не должно). Публичная страница фрейм не поднимает.
- [ ] Реквизиты издателя отображаются.
      ⚠ Эти четыре значения запекаются **на сборке**, а не на старте. Если их задали в окружении
      работающего процесса и ничего не появилось — это не дефект, нужна пересборка.
