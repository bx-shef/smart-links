# Публикация в Маркете: чек-лист и обоснование доступов

> Last reviewed: 2026-07-29

Что нужно закрыть перед подачей приложения в Маркет Битрикс24, и чем обосновывается каждый
запрошенный доступ. Обоснования нужны не только модератору: **список доступов расширяется тяжело**
— после публикации добавление скоупа требует повторного согласия на уже установленных порталах,
поэтому набор фиксируем осознанно один раз.

## 1. Обоснование доступов

Приложение просит шесть: `user_brief`, `crm`, `lists`, `placement`, `userfieldconfig`, `pull`.
Ниже — что именно вызывается и что сломается без доступа. Методы взяты из кода, а не по памяти.

| Доступ | Что вызываем | Зачем | Без него |
|---|---|---|---|
| `crm` | `crm.item.list`, `crm.item.update`, `crm.item.fields` | Прочитать карточку-источник, показать кандидатов, записать и убрать связь, предложить поля в настройках | Приложение не работает вовсе — это его основная функция |
| `lists` | `lists.get`, `lists.element.get`, `lists.get.iblock.type.id` | Цель связи — элемент Списка: перечислить списки, найти элементы, определить раздел списка | Половина функции отваливается: цель «элемент Списка» недоступна |
| `placement` | Регистрация и работа обработчика поля, слайдеры настроек и обратной связи | Поле рисуется прямо в карточке — это и есть способ доставки функции | Поле негде показать |
| `userfieldconfig` | `userfieldtype.add`, `userfieldtype.delete` | Зарегистрировать тип поля «Умная ссылка» на установке | Тип поля не создать, администратору нечего добавить в карточку |
| `pull` | `pull.application.event.add` | Разослать открытым карточкам команду перечитать настройки после сохранения | Сотрудникам придётся перезагружать карточки вручную после каждой правки настроек |
| `user_brief` | Профиль текущего пользователя (`Profile`), в т.ч. признак администратора | Скрыть настройки от не-администратора; проверить фрейм-токен на сервере | Настройки поля стали бы доступны любому сотруднику портала |

⚠ **Именно `lists`, а не `list`.** Кода `list` в перечне доступов Битрикса нет; с ним
`lists.element.*` вернул бы `insufficient_scope`.

**Чего мы НЕ просим и почему это стоит сказать модератору:** `task`, `disk`, `telephony`, `im`,
`log`, `sale`, `catalog`. Приложение не читает задачи, не трогает файлы и не пишет в ленту.

### Событийная подписка

`event.bind` / `event.get` / `event.unbind` — на `ONAPPINSTALL` и `ONAPPUNINSTALL`. Подписка
обязательна не для функции, а для **гигиены данных**: без неё уведомление об удалении приложения не
приходит, и ключи доступа клиента остались бы у издателя навсегда. См. `DATA_POLICY.md`.

## 2. Что заполнить перед подачей

Это то, чего в коде нет и быть не может — нужны реальные данные владельца. Всё подставляется через
переменные окружения; **пока переменная пуста, блок на странице не рендерится вовсе**, чтобы на
юридической странице не оказалось правдоподобной заглушки.

⚠ **Все четыре переменные запекаются на СБОРКЕ, а не на старте.** Лендинг и `/privacy`
пререндерятся в статический HTML, поэтому значение, выставленное только в окружении работающего
процесса, в страницу не попадёт — и это выглядит как «я всё задал, а ничего не появилось».
Проверено: с пустыми переменными на сборке подвал показывает одну ссылку на политику, после
пересборки с заданными — все три и реквизиты. Задавать их нужно **в окружении сборки**, а после
изменения — пересобирать.

- [ ] `NUXT_PUBLIC_SUPPORT_EMAIL` — адрес поддержки. Появится в подвале лендинга и в политике
      конфиденциальности.
- [ ] `NUXT_PUBLIC_PUBLISHER_DETAILS` — реквизиты ИП (наименование, УНП/ИНН, адрес). Появятся там же.
- [ ] `NUXT_PUBLIC_B24_MARKET_CODE` — код приложения в Маркете. Включает ссылку «Страница в
      Маркете» в подвале и попап оценки.
- [ ] `NUXT_PUBLIC_SITE_URL` — постоянный публичный адрес. Без него не будет canonical и og:url.
- [ ] Срок ответа на запрос об удалении данных — вписать в `DATA_POLICY.md` и в `/privacy`.

## 3. Материалы карточки Маркета

- [ ] Название и короткое описание (взять из `landing.seo` — они уже написаны по правилам текстов).
- [ ] Подробное описание: что делает, кому, чем отличается от обычного поля-ссылки.
- [ ] Скриншоты — снимаются в живом прогоне, пункты помечены 📷 в
      [`MANUAL_TEST_PLAN.md`](MANUAL_TEST_PLAN.md). Минимум: поле в карточке со связью, подбор,
      экран настроек, вид на телефоне.
- [ ] Иконка приложения.
- [ ] **og:image** для лендинга (1200×630). Сейчас не задан: `useSeoMeta` на `/` отдаёт
      `twitterCard: 'summary'` без картинки. Когда картинка появится — положить в `public/og.png`,
      добавить `ogImage`/`twitterImage` (абсолютный URL из `siteUrl`) и переключить карточку на
      `summary_large_image`.
- [ ] Ссылка на политику конфиденциальности: `<site>/privacy`.
- [ ] Ссылка на поддержку.

## 4. Технические предусловия

- [ ] Приложение развёрнуто по постоянному адресу с валидным TLS.
- [ ] `pnpm check` и CI зелёные на релизном коммите.
- [ ] `GET /api/health` отвечает 200.
- [ ] `B24_TOKEN_ENC_KEY` задан (иначе установка отвечает 503 — это by design, но в проде это
      означает «никто не поставит»).
- [ ] `B24_APPLICATION_TOKEN` **либо задан настоящим значением, либо не задан вовсе.** Заглушка
      вроде `xxx`/`changeme` выглядит здорово и при этом отвергает каждую первую установку с 403 —
      `checkAppEnv` специально ругается на такое при старте.
- [ ] Проверено, что за прокси `APP_EDGE_SECURITY` **выключен** (два CSP браузер пересекает
      рестриктивно), а без прокси — включён.
- [ ] Список зон Битрикс24 (`B24_ZONES`) сверен с реальным Маркетом; отсутствующие добавлены через
      `B24_EXTRA_ZONES`. Сейчас список собран по наблюдениям.
- [ ] Внешний суточный пинг настроен: целевая платформа усыпляет процесс, а продление токенов
      завязано на проходы по расписанию (см. `DEPLOY_VIBECODE.md`).

## 5. Живой прогон

- [ ] [`MANUAL_TEST_PLAN.md`](MANUAL_TEST_PLAN.md) пройден целиком, итоговая таблица заполнена.
- [ ] Блокеры из него закрыты: установка с нуля, работа поля, приход `ONAPPUNINSTALL`.
- [ ] Открытые вопросы (тёмная тема, адреса открытия элементов Списка по разделам) записаны в
      задачи, а не забыты.

## 6. Известные ограничения — сказать в описании, а не прятать

Модератор и первый же клиент найдут их всё равно; заявленное ограничение — это честность, а
найденное — это отзыв в одну звезду.

- Цель в CRM — только **Сделка**. Прочие типы записей требуют доработки.
- В режиме редактирования карточки поле не работает (сообщает об этом само).
- Элемент Списка открывается в новой вкладке, а не в слайдере портала.
- Открытие элемента Списка проверено для обычных списков портала; для других разделов приложение
  предупреждает прямо в настройках.
- Интерфейс только на русском.

## 7. После публикации

- [ ] Проверить установку **из Маркета** (не по прямой ссылке) на чистом портале.
- [ ] Убедиться, что попап оценки ведёт на реальную страницу приложения.
- [ ] Завести канал, куда попадают отзывы, и назначить, кто их разбирает.
